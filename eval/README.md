# Evaluation: router vs BM25 on synthetic notes

Deterministic, with no model calls. Every number measures a retrieval policy over fixed files and fixed labels,
**not model performance**. The generated results are in [`results/summary.md`](results/summary.md) (tables and
every failure case), [`results/summary.json`](results/summary.json) and [`results/raw.jsonl`](results/raw.jsonl)
(one row per condition × request).

## Data
- **Vault:** [`fixture_root/`](fixture_root/), generated by [`build_fixtures.py`](build_fixtures.py). 37 candidate notes:
  10 ideas, 8 jobs, 10 projects, 6 session checkpoints, a decisions note and 2 career files. All invented.
- **Requests:** 41 hand-labelled requests in [`requests.jsonl`](requests.jsonl): 12 exact, 10 paraphrase,
  6 confusable (near-duplicate entities), 6 ambiguous (correct behaviour is to load no entity note), 3 planning,
  3 job-prep (two required files), 1 cv-evidence.
- Each request lists its required notes. Where defensible it also lists "acceptable" notes, which are neither
  required nor counted as unrelated.

## Conditions
All conditions produce the same packet format (`memory.assemble_packet`).

| condition | what chooses the notes |
| --- | --- |
| `router_oracle` | The router, given the **labelled** route and slug. Perfect recall is by construction: this measures the packet policy given a correct choice. |
| `router_lexical` | The router, with route and slug chosen by a **label-free** lexical picker: BM25 over index titles and descriptions. It abstains to the index if the top score is < 2.0 or < 1.25× the runner-up. It stands in for the agent. By construction it can output only a category's default route or its `planning` fallback, **so it can never select `job-prep` or `cv-evidence`**. Those 4 requests are guaranteed misses. |
| `bm25_top1`, `bm25_top3` | BM25 over the full text of every note, plus the same default set. |
| `full_dump` | Every file: 35,256 characters, about 3× the router's 12,000-character cap. The router would refuse it, so it is an **over-cap context-cost reference, not a usable bounded baseline**. |

Parameters were fixed before the first run and not tuned. The labels, fixtures and router come from the same
author, and n = 41, so treat the differences as indicative only.

## Results
| condition | all required notes retrieved | recall | requests with unrelated notes | unrelated / request | ambiguous: abstained | packet chars, median (max) |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| `router_oracle` (labelled choice) | 35/35 | 1.00 | 0/41 | 0.00 | 6/6 | 4,378 (5,112) |
| `router_lexical` (label-free) | 21/35 | 0.64 | 10/41 | 0.24 | 2/6 | 4,370 (5,112) |
| `bm25_top1` | 24/35 | 0.74 | 10/41 | 0.24 | 0/6 | 4,355 (4,433) |
| `bm25_top3` | 31/35 | 0.93 | 41/41 | 1.93 | 0/6 | 5,677 (5,918) |
| `full_dump` (over-cap reference) | 35/35 | 1.00 | 41/41 | 35.78 | 0/6 | 35,256 (35,256) |

On the 31 requests the lexical picker can route (all but job-prep and cv-evidence), it retrieves every required
note on **21/31**. `bm25_top1` does so on **24/31**.

- **With a correct choice** (by construction), the router loads every required note and nothing unrelated. It
  also abstains correctly on all 6 ambiguous requests. `bm25_top3` comes close on recall but loads about 2
  unrelated notes per request and never abstains.
- **With the label-free picker, the router does worse than BM25 top-1.** The design moves the hard problem to the
  agent's route and slug choice. This eval does not show that a model makes that choice well.
- **Failure cases** (all listed in `results/summary.md`):
  - The picker misses 6 of 10 paraphrases, e.g. "the thing that tells me when the sea is highest".
  - Its "no match → planning" fallback loads `DECISIONS.md` on 4 ambiguous requests.
  - BM25 top-1 ranks a session checkpoint above the note it checkpoints 3 times, and loads a note on every ambiguous request.
- **Latency** is not a differentiator at this scale. In-process retrieval is under 1 ms median for the router and
  BM25, and 4–6 ms for the full dump. A CLI call costs 40–50 ms, of which about 19 ms is bare Python startup.
  Timings vary between runs; `summary.json` holds one run.

## Reproduce
```sh
python3 eval/run_eval.py          # rewrites results/raw.jsonl, summary.json, summary.md
python3 -m unittest test_eval     # fixtures rebuild byte for byte; a rerun matches raw.jsonl except timing
```
